# Phase 18 — Packaging and host registration

> Plan ID: IP-18
> Status: See README.md execution tracker
> Execution owner: release and packaging implementer
> Dependencies: IP-03, IP-06, IP-15, IP-17
> Parallel boundary: IP-19 after the artifact, registration, and compatibility contracts are stable
> Requirement IDs: NFR-010 (primary); FR-001, FR-015, NFR-007, NFR-009, operational compatibility and installer/updater/reset/uninstaller idempotency rules (supporting)
> Owned paths: `packaging/config/release-manifest.json` (to-create); `packaging/config/extension-ids.json` (to-create); `packaging/extension/chrome/manifest.json` (to-create); `packaging/extension/edge/manifest.json` (to-create); `packaging/host/chrome/com.infoboard.host.json.tmpl` (to-create); `packaging/host/edge/com.infoboard.host.json.tmpl` (to-create); `packaging/installers/linux/` (to-create); `packaging/installers/macos/` (to-create); `packaging/installers/windows/` (to-create); `packaging/release/` (to-create); `fixtures/packaging/phase-18/` (to-create); `tests/packaging/phase-18/` (to-create)

## 1. Mục tiêu

- Define one reproducible release input that produces the Chrome Web Store extension package, the Edge Add-ons extension package, and Native Messaging host installers for Linux, macOS, and Windows. Every generated artifact must declare the same product, protocol, ranking, and storage compatibility tuple.
- Define the exact browser permission set and Native Messaging registration boundary. The installed host must accept only the two declared extension identities, use an absolute executable path, and never silently accept an unresolved ID, a broad origin, or an unknown package.
- Define safe, repeatable install, upgrade, repair, rollback, and uninstall behavior. A failed integrity check, version check, registration check, or health check fails closed, preserves the last known-good installation when possible, and gives the user a concrete repair path.
- Make NFR-010 measurable across Chrome and Edge desktop on Linux, macOS, and Windows while preserving FR-001's command entry point and FR-015's owned-data cleanup boundary. Packaging must not add a network or browser-data dependency to the local hot path.
- Keep ownership explicit: IP-03 owns the extension runtime manifest and command behavior, IP-06 owns host process lifecycle, IP-15 owns reset/uninstall data semantics, and IP-17 owns privacy and permission review. This phase owns release assembly, installer registration, artifact integrity, and cross-component compatibility checks.

## 2. Phạm vi

- Bao gồm:
  - **Release source of truth.** Create `packaging/config/release-manifest.json` as the only release input for product name/ID, product version, Chrome and Edge package versions, host version, protocol major/minor, ranking model version, SQLite schema version, host name, target browsers/OSes, exact extension IDs, permissions, artifact names, and compatibility allowlists. A release cannot be built when an ID, version, target, or checksum input is missing or contains an unresolved placeholder.
  - **Chrome Web Store package.** Build a deterministic MV3 archive named `infoboard-extension-chrome-v<product_version>.zip` from the extension output. Its manifest has `manifest_version: 3`, the IP-03 service-worker, browser action popup `dist/search/surface-shell.html`, the single configurable `open-search` command, and exactly these permissions: `nativeMessaging`, `storage`, `tabGroups`, `tabs`, and `windows`. The `storage` permission is limited to the REF-013 `chrome.storage.local` key `profile_id`; `action` is a manifest key, not a permission. It has no `host_permissions` key (an empty array is the only equivalent if the store tooling requires the key) and no other browser permission.
  - **Edge Add-ons package.** Build `infoboard-extension-edge-v<product_version>.zip` with the same browser action popup and service-worker manifest, command and permission set, using the Edge package identity from the release manifest. Browser-namespace differences stay inside the IP-03 adapter; package assembly must not fork product behavior or introduce an additional command.
  - **Native Messaging host registration.** Use the fixed host name `com.infoboard.host` and `type: "stdio"`. Generate one browser-specific manifest per installation directory. The Chrome manifest's exact allowlist is `["chrome-extension://<chrome_web_store_extension_id>/*"]`; the Edge manifest's exact allowlist is `["chrome-extension://<edge_addons_extension_id>/*"]`. The angle-bracket names are release-config fields substituted with literal 32-character extension IDs before packaging; they are not runtime wildcards. The installer MUST reject an unresolved token, an empty list, an ID outside the release manifest, an extra origin, or any origin other than the required `/*` path suffix. There is never an origin value of `*`.
  - **Exact platform registration paths.** On Linux, install the host binary under `$XDG_DATA_HOME/InfoBoard/host/infoboard-host` (default `$HOME/.local/share/InfoBoard/host/infoboard-host`) and write browser manifests to `$XDG_CONFIG_HOME/google-chrome/NativeMessagingHosts/com.infoboard.host.json` and `$XDG_CONFIG_HOME/microsoft-edge/NativeMessagingHosts/com.infoboard.host.json` (defaulting to `$HOME/.config`). On macOS, use `$HOME/Library/Application Support/InfoBoard/host/infoboard-host` and `$HOME/Library/Application Support/Google/Chrome/NativeMessagingHosts/com.infoboard.host.json` plus `$HOME/Library/Application Support/Microsoft Edge/NativeMessagingHosts/com.infoboard.host.json`. On Windows, use `%LOCALAPPDATA%\InfoBoard\host\infoboard-host.exe`, per-browser manifest files below `%LOCALAPPDATA%\InfoBoard\native-messaging\`, and only the HKCU registration keys `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.infoboard.host` and `HKCU\Software\Microsoft\Edge\NativeMessagingHosts\com.infoboard.host`, whose default values point to those manifests. The installer must not write HKLM or a system-wide registration without a separately approved product decision.
  - **Compatibility and fail-closed behavior.** The extension hello advertises its product, browser, protocol, and extension versions; the host hello acknowledgement advertises host, protocol, ranking, storage schema, and limits. The release manifest contains an explicit compatibility tuple/allowlist rather than inferred version ranges. A major protocol or ranking incompatibility, unknown future schema, product mismatch, browser mismatch, or unsupported extension/host pair stops before tab data is sent or accepted and surfaces the IP-07 repairable `PROTOCOL_MISMATCH`/upgrade-required status. The current known-good installation remains active when an update cannot pass compatibility or health verification.
  - **Integrity and provenance.** Produce a lexicographically sorted `SHA256SUMS` for every extension archive, host payload, installer, generated host manifest, and release metadata file. Build archives with normalized file order, normalized permissions, fixed `SOURCE_DATE_EPOCH`, and no symlinks, path traversal entries, absolute archive paths, or untracked files. Verification checks the checksum before extraction, after staging, and after registration. A signature MAY accompany the checksum file, but checksum verification is mandatory and must not depend on a network service or a secret committed to the repository.
  - **Install.** Verify the artifact set, target OS/browser, checksums, manifest schema, exact permissions, extension IDs, ownership marker, and compatibility tuple before mutating user paths. Stage into a versioned InfoBoard-owned directory, write restrictive user-only permissions/ACLs, atomically publish the host and manifests, register only selected supported browsers, run the browser-mediated hello/health smoke check, and record the successful version only after the check passes. Re-running install on the same verified version is a no-op that still re-verifies integrity; a partial prior install is completed or repaired without duplicate registry values.
  - **Upgrade and migration.** Stage the new release beside the current release, retain one last-known-good backup, preserve profile-scoped configuration when IP-08 declares the schema compatible, and run transactional schema migration only through IP-08. Do not remove the old binary or manifest until the new host passes launch, registration, hello, protocol/ranking compatibility, and health checks. A failed migration or smoke check restores the old registration and binary atomically and reports a retryable upgrade failure.
  - **Repair and rollback.** Repair compares the ownership manifest, checksums, registration paths, registry keys, permissions/ACLs, and runtime compatibility against the release contract. It rewrites only missing or corrupted InfoBoard-owned artifacts and refuses to delete unknown files or follow links outside the allowlist. Rollback selects the last verified backup, verifies its checksums and compatibility before publishing, then repeats the health check. If no verified backup exists, rollback leaves the current files untouched and reports the exact recovery action (reinstall a verified compatible release); neither path closes or changes browser tabs.
  - **Uninstall.** Coordinate with IP-15's owned-path manifest to stop the host, remove the extension package through the browser/store path, remove the exact browser manifests, host binary, staging/backup artifacts, InfoBoard-owned database/cache/logs, and the two HKCU keys when present, then verify absence. Missing paths and already-removed registry values are successful no-ops. Permission failures remain actionable instead of becoming false success. Uninstall never closes tabs, modifies browser history, touches another profile, or removes unrelated files.
  - **Platform and browser matrix.** Exercise Chrome and Edge independently on Linux, macOS, and Windows, including clean install, repeat install, upgrade, failed upgrade/rollback, repair after deleting one owned artifact, host absence, extension/host mismatch, and repeat uninstall. Any unsupported OS/architecture combination is rejected before mutation and recorded in the release artifact metadata; it is not silently treated as supported.
  - **Scope boundary.** Installation is offline and local after receiving a verified release artifact. The plan covers browser package assembly and host registration, not browser-store credentials, browser API implementation, Go host internals, protocol serialization, tab projection, ranking logic, settings semantics, or diagnostics UI. It adds no loopback listener, page evaluation, remote service, or unbounded local data source.
- Ngoài phạm vi:
  - IP-03 remains the owner of the extension's runtime manifest, command handler, service-worker lifecycle, and browser adapter. This phase packages that output and rejects permission drift; it does not implement the command or focused search surface.
  - IP-06 remains the owner of Go process bootstrap, Native Messaging framing/session lifecycle, cancellation, and health state transitions. This phase launches and smoke-checks the host but does not duplicate its runtime state machine.
  - IP-15 remains the owner of profile configuration, reset semantics, InfoBoard data retention, and the authoritative uninstall ownership manifest. This phase invokes that contract from installers and does not create a second cleanup policy.
  - IP-17 remains the owner of privacy threat modeling, sensitive-field redaction, and permission/retention review. This phase enforces the resulting allowlist and does not expand data collection.
  - No browser-history source, page-content read, cookie or local-storage access, cloud account, telemetry endpoint, or application-owned listening port is introduced.

## 3. Điều kiện tiên quyết

- IP-03 has frozen the MV3 extension output contract, `open-search` command, exact minimal browser permission set, package adapter seam, and Chrome/Edge namespace handling. The packaging manifests must consume that contract without adding permissions.
- IP-06 has supplied the Go host executable contract, startup/exit behavior, Native Messaging stdin/stdout ownership, bounded launch/shutdown behavior, and a health handoff usable by an installer smoke test.
- IP-15 has supplied the profile-scoped configuration/reset/uninstall contract and the reviewed InfoBoard-owned path manifest. IP-18 may add registration artifacts to that manifest only through an explicit interface; it must not broaden deletion by scanning a parent directory.
- IP-17 has completed the permission matrix, origin trust boundary, file/ACL policy, private-context separation, log/retention audit, and abuse cases. The release checklist must block any artifact that violates those decisions.
- IP-07's envelope and compatibility rules are available to the implementation even though IP-07 is not a direct dependency of this phase: hello/hello_ack, typed mismatch errors, bounded payloads, and fail-closed version negotiation are the smoke-check contract.
- The canonical product boundary, architecture, requirements, packaging operations, persistence lifecycle, runtime protocol, domain privacy, and verification documents are available under `docs/plan/refactor/`. The implementation roots are currently absent, so every path in this plan is a logical `to-create` target, not an observed file.
- Release engineering has an approved, non-secret mapping from Chrome Web Store and Edge Add-ons listings to their literal extension IDs. Private signing material is provided by the release environment, never stored in Git, and is not required for local fixture verification. Builds must fail when the mapping is absent rather than substituting a test or wildcard ID.
- A browser fixture harness can launch each declared browser with the packaged extension, select a profile, invoke the command, and exercise a Native Messaging hello/health exchange. An offline fixture mode must validate archive, manifest, and registry output without requiring a live store account.

- [ ] `packaging/host/chrome/com.infoboard.host.json.tmpl` and `packaging/host/edge/com.infoboard.host.json.tmpl` (to-create): templates that produce the fixed host name, `stdio` type, resolved absolute binary path, and one exact browser-specific `allowed_origins` entry.

Linux/macOS scripts must not require a root install for the supported per-user layout; Windows uses HKCU only.
- [ ] `packaging/release/` (to-create): deterministic build, manifest-generation, checksum, artifact-verification, compatibility-check, and lifecycle-fixture entry points. Generated artifacts use stable names such as `infoboard-extension-chrome-v<product_version>.zip`, `infoboard-extension-edge-v<product_version>.zip`, platform host installer archives, and sorted `SHA256SUMS`.
- [ ] `fixtures/packaging/phase-18/` (to-create): valid Chrome/Edge package fixtures, exact-origin fixtures, each OS registration layout, matching and mismatching version tuples, changed checksums, malformed manifests, extra origins, permission drift, path traversal/symlink entries, absent/corrupt owned files, failed health checks, upgrade rollback, and already-removed cleanup cases. Each fixture records expected observable status and untouched browser state.
- [ ] `tests/packaging/phase-18/` (to-create): focused artifact reproducibility, manifest/permission/origin checks, checksum verification, install/upgrade/repair/rollback/uninstall idempotency, mismatch fail-closed, path safety, and Chrome/Edge × Linux/macOS/Windows registration tests.
- [ ] Release evidence bundle (generated, not hand-edited): sorted checksums, build input digest, compatibility tuple, browser/OS matrix, registration inspection output, health smoke output, rollback result, and post-uninstall owned-path absence result. No raw title, URL, query, token, or secret may appear in the bundle.

## 9. Rủi ro và quyết định còn mở

- Rủi ro: Store-issued extension IDs can change if a package is republished under a different listing or signing identity.
  - Phương án xử lý đã chọn: Treat the approved Chrome/Edge IDs as release configuration, generate exact origins from that mapping, reject missing/unresolved IDs, and require a new release review when either listing identity changes.
- Rủi ro: A host update can pass file checks while failing protocol, ranking, or schema compatibility at runtime.
  - Phương án xử lý đã chọn: Require an explicit compatibility tuple plus browser-mediated hello/health before commit, retain one verified rollback, and fail closed before accepting a snapshot when any required version differs.
- Rủi ro: Platform path, ACL, registry, or browser startup differences can make a nominally valid installation unusable.
  - Phương án xử lý đã chọn: Keep per-platform adapters behind one lifecycle contract, use per-user paths and HKCU, run a real registration/health smoke check, and require evidence for every NFR-010 matrix cell.
- Rủi ro: Repair or uninstall could delete a user file placed near an owned path.
  - Phương án xử lý đã chọn: Use explicit ownership markers and exact path/registry allowlists, reject symlinks and unexpected parents, and preserve unknown files even when cleanup is incomplete.
- Rủi ro: Reproducible archives can drift because file timestamps, compression, or tool versions differ.
  - Phương án xử lý đã chọn: Pin the build toolchain in release metadata, set `SOURCE_DATE_EPOCH`, normalize ordering/modes, record input digest, and compare two clean builds before publishing.
- Câu hỏi còn mở chỉ khi câu trả lời có thể thay đổi contract: What literal store IDs and target CPU variants are approved for the release matrix? Implementation must block publication until the release owner supplies them; it must not guess or widen support.
